# CloudWay — design guideline

Covers what the site looks like and how each page functions. Read alongside
`02_ARCHITECTURE.md` (this doesn't change any backend rule) and
`04_ASSIGNMENT_REQUIREMENTS.md` (CSS: external + internal + inline is an
explicit rubric line — see "CSS architecture" below for exactly where each
one goes).

## Design philosophy

Clean, calm, and credible — a study tool, not a marketing site. Cloud
platforms (AWS included) lean on navy/dark-slate backgrounds with a single
warm accent colour; CloudWay follows that convention loosely without copying
AWS's actual brand assets (no AWS logo, no "Squid" orange used exactly as
AWS uses it — pick your own accent, e.g. a teal or amber, to stay clearly
your own product). Every screen should answer "where am I, what can I do
here, what happens if I click this" at a glance. No decorative animation, no
stock-photo hero banners — content and progress are the visual interest.

## Colour palette (starting point — replace hexes if your team has brand colours)

| Role | Colour | Hex | Usage |
|---|---|---|---|
| Primary / brand | Deep navy | `#0B2545` | Header, nav background, primary buttons |
| Accent | Teal | `#13A89E` | Links, active states, progress bars, CTAs |
| Accent (alt, sparingly) | Amber | `#F2A93B` | Highlights, "in progress" badges — never both accents on one element |
| Background | Off-white | `#F7F8FA` | Page background |
| Surface | White | `#FFFFFF` | Cards, forms, tables |
| Text primary | Near-black | `#1B1F27` | Body text, headings |
| Text secondary | Slate grey | `#5B6472` | Meta text, timestamps, helper text |
| Border | Light grey | `#E1E4E8` | Card borders, table dividers |
| Success | Green | `#2E9E5B` | Correct quiz answer, "published" status |
| Danger | Red | `#D3453A` | Validation errors, "delete" actions, lockout messages |
| Warning | Amber (same as accent-alt) | `#F2A93B` | Low quiz score, near-lockout warning |

Rule: one accent does the heavy lifting (teal) — amber is a secondary
highlight only, never the default button colour. Never use colour alone to
convey meaning (pass/fail, published/draft) — always pair with text or an
icon, for anyone who can't distinguish the colours.

## Typography

- **Headings:** "Poppins" (Google Fonts) — weight 600 for h1/h2, 500 for
  h3+. Confident but not decorative.
- **Body:** "Inter" (Google Fonts) — weight 400 body, 500 for emphasis. No
  weight above 600 anywhere; nothing italic except quoted feedback text.
- **Scale:** h1 28px, h2 22px, h3 18px, body 16px, small/meta 13px.
  Line-height 1.5 for body, 1.25 for headings.
- Load both via `<link>` to `fonts.googleapis.com` in `Site.master`'s
  `<head>` (and `Admin.master`'s) — this is one legitimate external resource,
  distinct from the "external CSS" rubric item, which is `site.css` itself.

## Layout and spacing

- Base spacing unit: 8px. Use multiples of it for all margin/padding (8, 16,
  24, 32, 48) — don't invent one-off values.
- Max content width: 1140px, centred, with 24px side padding on smaller
  screens.
- Grid: simple CSS Grid or Flexbox for card layouts (course catalogue,
  admin dashboards) — no CSS framework grid system needed for a site this
  size.
- Breakpoints: 960px (tablet), 640px (mobile). Nav collapses to a simple
  stacked/hamburger menu below 640px — one JS toggle, no framework.
- Card corner radius: 8px. Buttons: 6px. Consistent everywhere — don't mix
  radii.

## Icons

No icon font library needed for this scope — a handful of small inline SVGs
(checkmark, chevron, lock, user) covers everything used (nav, status
badges, form feedback). Keep each icon under ~10 path points; if an icon
needs to be more detailed than that, it's the wrong icon for this system.
Avoids adding an external icon-font dependency for a handful of glyphs.

## CSS architecture (this satisfies the explicit rubric line)

- **External:** `Content/site.css` — the real stylesheet. Colour variables
  (`:root { --primary: #0B2545; ... }`), typography, layout, all components
  below. This is the vast majority of the CSS.
- **Internal:** one page-specific `<style>` block is enough to satisfy this
  rubric item — the natural place is `LessonDetails.aspx`, since lesson
  content HTML (`<h3>`, `<ul>`, etc., per `03_DATA_MODEL.md`'s content
  decision) benefits from scoped rules that don't belong in the global
  stylesheet.
- **Inline:** one deliberate `style="..."` — e.g. a progress bar's fill
  width, which is legitimately dynamic per-enrolment and has to be inline
  (`style="width: 62%"`) rather than a static CSS class. This is also the
  most honest, least "tacked on" place to put it, since a real inline style
  attribute is doing actual work there, not just satisfying a checklist.

## Core components (defined once in site.css, reused everywhere)

- **Button** — primary (navy bg, white text), secondary (white bg, navy
  border/text), danger (red, for delete actions). One consistent height
  (40px), padding (12px 20px), radius (6px) across all three.
- **Card** — white surface, 1px light-grey border, 8px radius, 16–24px
  internal padding. Used for course tiles, lesson list items, admin summary
  tiles.
- **Form field** — label above input, 40px input height, 6px radius, grey
  border that turns teal on focus, red border + red helper text on
  validation failure (paired with the existing server-side `ValidationException`
  messages — the UI displays exactly what the BLL already returns, no new
  message strings invented in the UI layer).
- **Table** (admin grids) — white surface, light-grey row dividers, no
  vertical lines, row hover highlight, right-aligned action icons
  (edit/delete) per row.
- **Badge** — small pill, used for role (Admin/Student), publish status
  (Published/Draft), and quiz pass/fail. Colour + text together, never
  colour alone.
- **Progress bar** — track in light grey, fill in teal, percentage label
  beside it. This is the one inline-style use case above.
- **Alert/banner** — success (green-tinted background), error (red-tinted),
  used for form submission feedback and the lockout/attempts messaging from
  the auth UX enhancements.

## Navigation structure

- **Guest nav:** Home · Courses · Contact · Login · Register
- **Student nav (post-login):** Home · Courses · My Learning · [name/role
  badge, dropdown: Profile, Logout]
- **Admin nav:** separate `Admin.master` layout — sidebar with Categories,
  Courses, Lessons, Quizzes, Users, Feedback, plus a top bar showing
  [Admin name, Logout]. Admins can also reach the public/student nav (per
  `Project_documentation.pdf`'s note that an Admin account is still a normal
  member underneath) via a small "View site" link back to `Site.master`.
- Breadcrumbs on every non-home page, sourced from `Web.sitemap` as in the
  base repo — don't rebuild this mechanism, only restyle it.

## Page-by-page functional design

**Home (`Pages/Default.aspx`)** — hero strip with CloudWay's value
proposition in one sentence, 3–4 featured/published courses as cards below,
each showing category badge + title + one-line description. CTA button:
"Browse courses" (guest) or "Continue learning" linking to My Learning
(logged-in student).

**Course catalogue (`Pages/Courses.aspx`)** — filter bar (category
dropdown, keyword search — both server-side, reusing the existing
pagination pattern), grid of course cards below. Each card: title,
category badge, lesson count, "Enrol" button (or "View" if already
enrolled).

**Course details (`Pages/CourseDetails.aspx`)** — title, description,
category, ordered lesson list (locked/greyed for guests, clickable for
enrolled students), quiz summary block, Enrol/Unenrol button that swaps
based on `EnrollmentBLL` state — identity for this action comes from
session per `02_ARCHITECTURE.md`, never the query string.

**Lesson view (`Member/LessonDetails.aspx` or under `Pages/` per repo
convention)** — lesson title, rendered HTML content (the internal `<style>`
block lives here), "Mark complete" button, prev/next lesson navigation,
no video/resource UI this phase per `03_DATA_MODEL.md`.

**Quiz (`Member/Quiz.aspx`)** — one question per screen or a single
scrollable form (pick one, don't build both) with radio-button options,
submit button disabled until all questions answered (client-side check,
still server-validated), result screen showing score + pass/fail badge
immediately after submission — this is `QuizAttempts` being written.

**My Learning (`Member/MyLearning.aspx`)** — enrolled courses as cards with
a progress bar each (the inline-style use case), a quiz-history table
below (course, score, date, pass/fail badge) — this is the "student
dashboard" the CloudWay proposal promised.

**Login/Register (`Account/*.aspx`)** — centred single-column form, max
400px wide, on a plain background (no split-screen hero image — keep it
simple). Login includes the "remember me" checkbox and the
attempts-remaining messaging from the auth UX enhancements.

**Profile (`Account/Profile.aspx`)** — two clearly separated form
sections (edit profile / change password) with distinct `ValidationGroup`
values per `Project_documentation.pdf`'s own documented gotcha — don't
repeat that bug.

**Admin pages (`Admin/*.aspx`)** — consistent list-then-edit pattern per
entity: a table view with an "Add new" button and per-row edit/delete
icons, opening a form (same form-field styling as the public site) for
add/edit. No custom admin theme beyond the sidebar layout — reuse the same
component styles as the public site so there's one design system, not two.

**Contact (`Pages/Contact.aspx`)** — simple form, no login required,
confirmation banner (the alert component) on successful submission.

## Responsive behaviour

- Course/admin card grids: 3 columns desktop, 2 tablet, 1 mobile.
- Admin sidebar collapses to a top dropdown below 960px rather than an
  off-canvas drawer — less JS, same outcome.
- Forms are always single-column, so they need no responsive changes beyond
  the 640px container padding.

## What this guideline deliberately leaves out

No dark mode, no theming system, no design tokens beyond the CSS variables
above, no component library/framework. One light theme, one CSS file, a
handful of reused classes — consistent with `06_CODING_GUARDRAILS.md`.
